El fix de la migración 0004 reanudable ya estaba en `main` (PR #37 y #38), pero **faltaba la

`pytest` con la variable seteada aplicaba migraciones contra la base de desarrollo real.
Ahora usa `monkeypatch`.

### PR #72 — proxy same-origin de la API

`frontend/nginx.conf` pasó a proxear `/api/` al backend, de modo que el browser use una URL
relativa y no haya CORS. Dos correcciones sobre la idea original de la rama
`fix/cors-same-origin-proxy`:

1. Los `ARG` de build nunca llegaban al `RUN`: un `ARG` declarado antes del primer `FROM` es
   global y no lo ven las instrucciones de los stages. La versión anterior usaba
   `${BACKEND_INTERNAL_URL:-default}`, así que la variable llegaba vacía y caía siempre al
   default — el build "funcionaba" por defaults, no por configuración, y un valor distinto
   se ignoraba **en silencio**.
2. El `sed` se aplicaba sobre una copia en `/tmp`, no sobre el `default.conf` que nginx
   carga. Ahora se aplica sobre el archivo real y le sigue un `nginx -t`.

## Qué se rompió en el camino

**Producción quedó sin API entre las 08:19 y las 08:28.** La causa: los apps de producción
tenían `git_commit_sha` anclado a un commit del 30 de septiembre. El auto-deploy por webhook
ignora el anclaje, pero el deploy manual lo respeta, así que el deploy manual construyó
código viejo cuyo `nginx.conf` no tiene la ruta `/api/`, mientras el bundle sí venía con la
URL relativa. El login devolvía el HTML del SPA con 405.

Lo que agravó el error fue de método: en staging se verificó el bundle servido antes de dar
por buena la validación, y en producción no, porque "ya había funcionado una vez". Ese atajo
fue el que convirtió un deploy dudoso en una caída. La verificación que faltaba era la que
después confirmaba el problema.

Segundo hallazgo del mismo deploy: el **backend** de producción también estaba anclado, así
que quedó con código de septiembre contra un frontend de hoy. Hubo que redesplegarlo.

**Corrección de una hipótesis mía:** busqué durante un rato un "nginx frontal" que cortaba
`/api/` en el host. No existe: el 502 lo genera el nginx del propio contenedor del frontend.
El `legacy-proxy` que aparece en `docker ps` no participa, escucha en un puerto sin publicar y
reenvía a otra máquina.

**En staging**, el primer intento de deploy dejó la app sin API porque `BACKEND_INTERNAL_URL`
apuntaba a la URL pública sslip, que no resuelve desde dentro del contenedor. Se revirtió
y se destapó la solución real.
